# PartyCombat

PartyCombat is a Windower 4 addon for deliberately coordinating physical
combat across multiboxed characters without handing movement to HealBot or
blindly mirroring the leader's selected target.

This addon was generated by OpenAI Codex for a six-character Valefor party:

- Leader: `Dolomedes`
- Puller: `Tackleberry`
- Default authorized attackers: all six characters, including `Dolomedes`
- Automatic pursuit limit: 10 yalms
- Explicit forced-pursuit limit: 30 yalms
- Directed split-pursuit limit: 50 yalms

It is intentionally conservative. Loading the addon does nothing until a
validated runtime policy has arrived and the configured leader or puller arms
it. Static `settings.lua` alone is not combat authorization.

## Behavior

### Quiet repeated explicit arm (v0.6.19)

The first `//pc on` acknowledgement remains visible. Repeating the same ON
while PartyCombat is already armed silently republishes its authority repair
without printing another green acknowledgement on every client.

### Silent orchestrator convergence (v0.6.18)

PartyTactics can internally send `//pc reconcile on` or `//pc reconcile off`
to repair one client's current ordered combat state without producing chat or
IPC. The operation is local and idempotent: repeated OFF repair does not
disengage later manual combat, and repeated ON repair does not repeat local
activation work. ON is accepted only while a validated runtime policy still
names that client; otherwise the client remains fail-closed and disarmed.

`reconcile` is an orchestration transport, not an operator command. Continue
to use `//pt arm` and `//pt disarm` so the whole party receives one ordered
intent. A direct `//pc on` or `//pc stop` retains its existing visible,
party-broadcast behavior.

### Acknowledgement-driven directed split and lane stop (v0.6.17)

`//pc forceidto <uint32> <attackers_csv>` sends one exact enemy only to the
named subset of the active policy's configured attackers. Other attackers and
target-only observers retain their current lanes. Damage by a controller on
its assigned directed target remains private instead of broadcasting that
target back to the entire roster; attacking a different enemy is still a
deliberate synchronization edge.

The directed handoff never scans or reacquires after a manual target change.
During a new exact edge, v0.6.17 tolerates only the one previous battle target
for up to 15 seconds and retransmits the exact request while the client crosses
the arena. This is an acknowledgement window, not a lasting target lock: it
ends immediately when the requested battle target is observed, and any third
battle target still yields to manual control. `//pc localstop` also cancels the
lane immediately. All controller, runtime-policy, live-enemy, exclusion, and
recipient validation remains in place. Its 50-yalm pursuit bound permits a
named add killer to cross a separated Ambuscade arena after the boss has been
pulled to a corner.

An attacker may now be intentionally omitted from the broad `targeters` list.
That **directed-only attacker** ignores ordinary shared-target broadcasts but
still accepts an exact `forceidto` addressed to it. `//pc stopto
<attackers_csv>` disengages only the named configured attackers, preserving the
loaded policy, controller authority, and every other lane. It is also a
one-shot edge: the next directed target can resume that attacker, and no loop
reclaims a later manual target. The Qutrub profile uses this to keep Tackle off
Bigwig, stop Tackle while no adds exist, and stop Dolo while an add generation
is being focused.

### Manual target handoff (v0.6.13)

Once the requested battle target is established, PartyCombat no longer
re-selects it merely because the operator tabs to another target. A manual
battle-target change or disengage yields the local target-maintenance lane;
late swings against the old shared target cannot reclaim it. The next explicit
force, synchronized target transition, or leader action against a different
enemy resumes automation. Authority stays armed, so this is an improvisation
handoff rather than a party-wide stop.

### Exact local one-shot engagement (v0.6.12)

`//pc engageonceid <uint32>` asks only the local controller client to enter
battle with one exact living, targetable, permitted enemy. It emits at most one
combat packet and does not arm synchronization, store an active/shared target,
broadcast IPC, face, approach, schedule a retry, or re-engage later. The command
is restricted to the configured leader or puller and rejects an invalid,
excluded, or unavailable entity ID.

This is the cooperative ranged-attacker path used by PartyTactics. A COR can
enter battle so normal ranged weapon skills are available without becoming a
PartyCombat targeter or allowing the addon to snap the character's target,
position, or facing afterward.

### Reliable explicit force (v0.6.9)

`//pc force` keeps its original behavior: it uses the configured controller's
current living enemy target. `//pc forceid <uint32>` provides the same operation
for an already resolved server entity ID, allowing a trusted orchestrator to
avoid cursor-dependent targeting. The ID must be a decimal integer from 1
through 4294967295 and must resolve locally to a living, targetable, permitted
enemy. Both commands remain restricted to the configured leader or puller.

An explicit forced-target message atomically authorizes a receiving targeter
only when that client already holds a validated runtime policy. This removes a
first-command race between separate authority and target messages without
letting a fresh or invalidated PartyCombat instance enter combat. Ordinary
`force` and `forceid` remain one-shot commands; there is no delayed snap-back
after the operator changes targets.

### Exact hidden-gauge force (v0.6.10; hardened in v0.6.11)

`//pc forceopaqueid <uint32> <exact_name>` is a separate opt-in route for an
encounter whose server entity can expose `hpp = nil`. It is accepted only from
the configured leader or puller after a fresh runtime policy, and only when the
resolved entity has the exact supplied name, ID, index, enemy type, targetable
state, permitted exclusion state, and current party claim. Spaces in the exact
name are encoded as underscores by the typed PartyTactics action API.

The receiver repeats all of those checks before accepting the target. In
v0.6.11 those exact checks complete before an inert follower can become
authorized or have HealBot combat controls cleared. The stored exception is
cleared by stop, invalidation, a target mismatch, zoning, logout, or unload.
Logout and unload also disengage any injected attacker, revoke runtime-policy
readiness, and cancel the one pending retransmit. Numeric HPP targets continue through the ordinary validation path;
`force`, `forceid`, automatic synchronization, exclusions, distances, and all
existing profiles retain their previous behavior. This exact hidden-gauge
route alone retransmits once after one second to tolerate battlefield entity
settle timing; the retry repeats every exact-name/ID/claim check.

### Exact local observer selection (v0.6.9)

`//pc observeid <uint32>` selects one exact enemy only on the client where the
command runs. It is accepted only when that client has a validated runtime
policy and is configured as a targeter but not an attacker. The decimal ID must
resolve locally to a living, targetable, permitted enemy within the 30-yalm
force limit.

A successful observer selection authorizes that local target-only observer and
injects only the non-combat target selection used by `<t>`-based support
controllers. It does not arm PartyCombat, broadcast IPC, inject an attack
packet, face, approach, or schedule a retransmit. This lets a profile runtime
select a resolved add for a local debuff controller without changing the
damage group's shared target.

### Profile-controlled target exclusions (v0.6.8)

PartyCombat has no global target exclusions. Static settings and runtime
policies default to `none`, so one fight cannot silently change target
selection for every other fight. A profile can opt into the `elemental`
exclusion by supplying it as the final `policy` argument.

When enabled, all configured characters reject monster names containing the
whole word `Elemental`, case-insensitively. This includes `Demon's Elemental`,
other summoned `... Elemental` enemies, and the eight ordinary elemental
names. `Elementalist` is not a match. The configured exclusion applies to
automatic, forced, encounter-priority, and peer-supplied targets; `//pc force`
cannot bypass it.

An excluded stored target is discarded. While combat is authorized, local
game/EasyFarm auto-targeting of an elemental is also released: the character
disengages from it and selects the retained allowed enemy, or self if none
exists. A rejected peer message never overwrites a valid shared target.
Selection cleanup does not move characters, change FastFollow, disable buffs
or healing, or alter GearSwap/equipment. Stopped PartyCombat does not override
manual targeting. Exclusion messages are limited to one per ten seconds.
AutoWS2 v0.3.3 provides a matching session-only
`//aws2 exclude elemental|none` guard; the profile must configure both layers.

EasyFarm must exclude them at acquisition too. Its **Ignored** list needs the
regular expression `\bElemental\b`. The local `Tackleberry.eup` and
`Tackleberry-PLD-PartyCombat.eup` have this rule; all other saved fields are
unchanged. Reload the updated profile after pausing EasyFarm, and do not save
the old in-memory profile over it first. The installed EasyFarm/Release
executables were checked directly: their ignore-list test precedes aggro
acceptance, unlike the mismatched source code shipped beside them. No
EasyFarm binary changes were needed.

For this Limbus session, copy `scripts/reload_no_elementals_safe.txt` into
`Windower/scripts`, pause EasyFarm, and run
`//exec reload_no_elementals_safe.txt` from Dolo. It stagger-reloads only
PartyCombat and AutoWS2, reapplies the PartyTactics Limbus profile, and leaves
combat disarmed. Load the updated EasyFarm profile, then use `//pt arm` from
Dolomedes and resume pulls; no PartyTactics ACK or check result is required.
`//pc status` must report `v0.6.19` and `Target exclusions: elemental`.

These are target exclusions, not immunity: elementals can still aggro or
damage the party, and area effects aimed at another enemy can still include
one. Unattended camp survival is not guaranteed by this exclusion.

### Target synchronization

PartyCombat follows combat actions, not cursor movement:

- Merely tabbing to another enemy does not move the followers.
- A resolved melee or ranged attack, weaponskill attempt, or damaging spell
  from the armed controller announces that enemy as the automatic combat
  target. Authorized Tackleberry can establish the first target by attacking
  it, which lets the PLD pull and acquire initial enmity without becoming the
  command leader. A miss still counts.
- A completed Flash from the configured puller announces the enemy in either
  stationary or mobile mode. Other non-damaging spells remain unable to
  redirect the party.
- The puller cannot redirect the party while a different synchronized target
  is still alive. Dolomedes remains the command authority and can override the
  puller by damaging another target.
- A runtime profile may name one encounter-priority enemy and a subset of its
  attackers. When that enemy becomes targetable, only those attackers split
  to it. Their attacks do not overwrite the shared tank/support target, and
  they resume that shared target after the priority enemy dies. Priority
  acquisition uses the existing 30-yalm forced-pursuit safety limit.
- Automatic target changes are accepted only when the enemy is within each
  follower's configured 10-yalm limit.
- `force` explicitly targets and engages the invoking controller's current
  enemy up to the configured 30-yalm safety limit. Mobile attackers approach;
  stationary attackers remain planted.
- `forceid` performs the same explicit operation for one validated server
  entity ID. It is intended for exact-target profile runtimes, not hand-entered
  persistent configuration.
- `forceidto` performs one exact-ID transition for only 1-6 named configured
  attackers. Its 50-yalm directed bound supports arena splits; it never
  redirects another attacker and never creates a persistent reacquisition
  rule.
- `stopto` performs one exact disengage for only 1-6 named configured
  attackers. It does not disarm the controller, revoke the policy, or stop any
  unlisted lane. A later directed target can resume them.
- `observeid` locally selects one validated server entity ID on a configured
  target-only observer. It does not arm or engage anyone and never changes the
  party's synchronized target.
- The attacker stops moving at 2.8 yalms.
- While it owns a valid combat target, PartyCombat explicitly faces the
  attacker toward that enemy, including when the attacker begins inside the
  2.8-yalm movement threshold.
- A stationary policy still synchronizes, faces, and engages every configured
  attacker, but PartyCombat never issues translational movement. The enemy must
  come into melee range. Mobile policies retain the normal 2.8-yalm approach
  behavior.
- A dead, despawned, or invalid target ends the pursuit.
- A runtime policy may authorize a character as a **target-only observer**.
  These clients receive the same local `<t>` as the damage group so RDM/BRD
  GearSwap can enfeeble it, but they never engage, face, approach, or interact
  with FastFollow. This is used by encounter profiles to
  keep the backline out of frontal mechanics without disabling Silence or
  Elegy.
- FastFollow is an independent user-owned controller. PartyCombat never sends
  it a start, stop, follow, redirect, or restore command—when arming, forcing,
  ending a target, stopping, changing policies, zoning, logging out, or
  unloading. If both addons are enabled, their movement requests may compete;
  the user must explicitly choose the desired FastFollow state per character.
- Zoning disarms the addon. Runtime role policies also load inert.
- A fresh load has no runtime role policy. `//pc on`, `//pc force`,
  `//pc forceid`, `//pc forceidto`, and `//pc observeid` require PartyStart,
  PartyTactics, or an
  explicit `//pc policy ...` command to install one. This is role routing, not
  an ACK, preflight, equipment, buff, or controller-proof gate. The local
  `engageonceid` command is deliberately separate and creates no persistent
  PartyCombat state.
- Only configured attackers move and engage. Configured target-only observers
  synchronize the target without entering combat; all other clients are inert.

PartyCombat clears inherited HealBot follow/assist/engage state when it
authorizes an attacker, but FastFollow state is never read or written. For a
stationary policy, manually stop FastFollow on every planted character before
arming PartyCombat; otherwise FastFollow can still move them even though
PartyCombat itself issues no translation. GearSwap remains responsible for
equipment, and AutoWS2 or another separately configured system remains
responsible for weaponskills.

## Installation

Copy the `PartyCombat` directory into `Windower\addons`, then load it on every
local client:

```text
lua load PartyCombat
```

All clients read the same `data\settings.lua` file. PartyCombat never writes
to it. This deliberately avoids Windower's shared XML config loader, which can
fail when several local clients reload an addon simultaneously.

Copy `scripts\reload_partycombat_safe.txt` to `Windower\scripts`. From a safe,
out-of-combat location, `//exec reload_partycombat_safe.txt` reloads only
PartyCombat, one client at a time. It never reloads GearSwap or an orchestrator.
Reapply the desired PartyTactics profile, then use `//pt arm`. Direct legacy
PartyStart or `//pc policy ...` users may still install and arm their own policy.

Recommended `scripts\init.txt` bindings:

```text
bind ^p exec salvage_duo_attack.txt
bind !p exec salvage_duo_off.txt
bind !o pcombat stop
```

Windower uses `^` for Control and `!` for Alt. For the direct Salvage duo,
Ctrl+P tells Kick to assist Dolo and attack while Alt+P sends Kick `/attack off`.
Neither key uses PartyCombat state. Alt+O is the general PartyCombat stop. Arming, force, and
party-wide stop commands are accepted from the configured command leader or
puller. Other clients can stop only their own local attacker.

For two-character Salvage farming, copy `scripts\salvage_duo_on.txt` and
`scripts\salvage_duo_off.txt` to `Windower\scripts`. Run
`//exec salvage_duo_on.txt` from Dolo. This installs a direct two-client policy:
Dolo remains manual. Ctrl+P directly tells Kick to assist Dolo and attack; Alt+P
directly tells Kick to disengage. It has no PartyCombat policy, PartyTactics
profile, six-client barrier, job check, preflight, or GearSwap weapon selection.

## Commands

```text
//pc on
//pc force
//pc forceid <uint32>
//pc forceidto <uint32> <attackers_csv>
//pc stopto <attackers_csv>
//pc engageonceid <uint32>
//pc forceopaqueid <uint32> <exact_name>
//pc observeid <uint32>
//pc stop
//pc localstop
//pc status
//pc help
```

- `on`: Arms automatic damage-target synchronization without selecting or
  approaching anything and without changing FastFollow. It refuses to arm if
  `status` says `support-ready No`.
- `force`: Arms synchronization and explicitly orders the configured attacker
  to target and engage the leader's current enemy. It approaches only when the
  active policy is mobile.
- `forceid <uint32>`: Arms and forces the living enemy represented by one
  validated decimal server entity ID. It has the same controller, exclusion,
  and distance restrictions as `force`.
- `forceidto <uint32> <attackers_csv>`: Arms and sends the exact living enemy
  once to only the listed configured attackers, with a bounded 50-yalm split
  pursuit. Other lanes remain untouched, and manual overrides are not
  reacquired.
- `stopto <attackers_csv>`: Disengages only the named configured attackers.
  The runtime policy and controller remain armed; other lanes continue and a
  later directed target edge can resume the stopped members.
- `engageonceid <uint32>`: Sends one local combat packet to the exact living,
  permitted enemy. It does not arm, broadcast, select a persistent target,
  face, move, retry, or re-engage. Use it when a ranged client needs battle
  state without PartyCombat ownership.
- `forceopaqueid <uint32> <exact_name>`: Profile-facing safety path for a
  party-claimed enemy whose HP percentage is unavailable. It binds only the
  exact live ID/index/name tuple, requires the party claim on every client,
  and is cleared on claim loss, invalidity, stop, policy replacement, or zone.
  Spaces in the exact name are encoded as underscores. Ordinary targets still
  require a numeric positive HPP value.
- `observeid <uint32>`: On a configured target-only observer, locally selects
  the living enemy represented by one validated decimal server entity ID. It
  applies the force-distance safety limit but does not arm, broadcast, engage,
  move, or retransmit.
- `stop`: Disarms synchronization, stops PartyCombat-owned movement, and
  disengages attackers. It leaves every FastFollow state unchanged.
- `localstop`: Fault-containment path used by PartyTactics. It stops only this
  Windower client and preserves the loaded roster; it never broadcasts a stop
  or changes another client.
- `reconcile on|off`: Internal PartyTactics convergence surface. It is silent,
  local-only, and idempotent; it is intentionally omitted from `//pc help`
  because operators should use the revisioned `//pt arm` and `//pt disarm`
  commands instead.
- `status`: Displays runtime support readiness, role, movement policy,
  authorization, target, mode, and the active target exclusions.
- `policy <name> <leader> <puller> <attackers> [targeters]
  [mobile|stationary] [priority_target] [priority_attackers]
  [target_exclusions]`: Validates and installs an in-memory role policy.
  Spaces in a priority target are encoded as underscores, for example
  `Bozzetto_Urchin`; use `-` for no priority.
  `targeters` defaults to the attacker list and movement defaults to `mobile`
  for backward compatibility. An explicitly supplied targeter list is exact:
  an omitted attacker becomes directed-only and can be controlled through
  `forceidto`/`stopto` without receiving broad shared-target updates.
  PartyTactics uses this command. Changing policy safely disarms combat, while
  reapplying an identical policy is idempotent. It never arms combat. The final
  field accepts `elemental` or `-` (none); unsupported exclusions reject the
  entire policy.

The normal PartyTactics flow is:

1. Apply the desired PartyTactics profile. It installs the PartyCombat role
   policy inertly; ACK and `//pt check` output is diagnostic only.
2. Position, then use `//pt arm` on Dolomedes. This sends `//pc on` immediately.
3. Let Tackleberry attack the first intended enemy, or target one on Dolomedes
   and use force.
4. Continue fighting normally. The followers switch to an enemy that
   Tackleberry establishes or Dolomedes overrides when it is within each
   follower's automatic leash.
5. Use `//pt disarm` to stop synchronized combat while retaining the selected
   support profile, or `//pt off` to tear the profile down.

## Configuration

Edit `addons\PartyCombat\data\settings.lua` to change the roster or limits.
The default table contains all six party members. Each entry uses the same
initial limits:

```lua
return {
    leader = 'Dolomedes',
    puller = 'Tackleberry',
    stationary = false,
    target_exclusions = {},
    attackers = {
        Dolomedes = {
            auto_distance = 10,
            force_distance = 30,
            engage_distance = 2.8,
        },
        Tackleberry = {
            auto_distance = 10,
            force_distance = 30,
            engage_distance = 2.8,
        },
        -- Additional character entries use the same fields.
    },
}
```

Attackers can be added or removed as character-named entries. Each client must
read the same configuration. PartyStart can replace the leader, puller,
attacker roster, synchronized targeter roster, movement policy, and an
optional named-priority attacker subset in memory through a validated
composition/profile policy; distance limits are retained
from the matching static character entries. Static settings without a `targeters`
table retain the old behavior in which targeters equal attackers. The old
`data\settings.xml` is ignored and may be retained as a historical backup.

## Support-orchestrator and AutoWS2 integration

PartyStart and PartyTactics select the command leader, puller, attackers, and
target-only observers. PartyTactics applies those roles best-effort per client;
ACKs and setup checks are diagnostic. `//pt arm` sends `on` immediately, and a
profile runtime may use the typed force, observe, and one-shot surfaces for its
exact strategy. PartyCombat remains the only owner of its synchronized target
selection, approach movement, engagement, and disengagement. `//pstart off` or
`//pt off` stops the support it owns and disarms PartyCombat while leaving
FastFollow untouched.
PartyStart's unattended `master` (Apex Efts), `apexbats`, `locusbats`, and
`apexcrabs` profiles send `stationary`. Limbus also sends `stationary`, keeping
the whole party fixed while Tackleberry pulls with Flash. Other supplied
profiles send `mobile`. Future fixed-camp profiles should explicitly set
`stationary = true`. A direct `policy` command that omits movement remains
mobile for backward compatibility. FastFollow must be stopped independently
on stationary party members before these profiles are armed.

The supplied Ambuscade V1 profile assigns `Bozzetto Urchin` to Dolomedes and
Kickpuncher. Tackleberry, Smalls, and Achoo keep attacking Bozzetto Breadwinner.
Barney is deliberately excluded from target synchronization so his camera
remains free for watching Housemaker.

## Safety and limitations

- This is a live-test prototype. Begin on harmless enemies in an open area.
- In mobile mode, movement is a straight line and does not path around walls,
  hazards, or additional enemy groups. Stationary mode issues no translational
  movement, but still synchronizes, turns, faces, and engages attackers.
- PartyCombat never changes FastFollow. Disable or redirect FastFollow
  yourself whenever its existing state conflicts with mobile approach or a
  stationary camp. PartyCombat stop and target death will not restore a
  preferred follow target because the addon no longer owns that preference.
- Facing is maintained only while PartyCombat owns a valid combat target; it
  does not rotate characters merely because the addon is armed.
- The automatic leash is measured from the attacker to the enemy, not from the
  leader.
- Damaging area-of-effect actions select the first valid enemy reported in the
  action packet.
- Priority matching is exact and requires a living valid target in Windower's
  mob array. Invisible or dormant encounter entities are ignored until the
  game exposes them as targetable. If several exact matches are active, the
  current one is retained; otherwise the lowest entity ID is chosen.
- Non-damaging enfeebles do not change the automatic combat target, except a
  completed puller Flash in either movement mode.
- Target-only observers have their local target reasserted while an armed,
  synchronized enemy remains alive. Manual target selection on those clients
  is therefore temporary until PartyCombat is stopped or the enemy ends.
- The configured puller may arm or force PartyCombat directly. Automatic
  puller authority can establish a target but cannot replace a living
  synchronized target.
- For an ordinary mobile EasyFarm puller, disable its job-ability, spell, and
  weaponskill battle lists. Limbus may instead leave only Flash enabled for
  Tackleberry: that completed Flash establishes the shared target, after which
  PartyCombat, PartyStart, GearSwap, and AutoWS2 own the combat policy.
- For any stationary unattended-XP camp, use exactly one enabled EasyFarm Pull
  action: `Flash`. Set Detection Distance to `20.9` (the maximum reliable
  player spell-casting distance), Wander Distance to `0`, and Approach off.
  Set the Flash row's EasyFarm Distance to `50`, the UI maximum.
  That value is intentionally not Flash's real range: it disables EasyFarm's
  unconditional pull-action navigation helper. Windower's `range=12` value for
  Flash is a resource range code that EasyFarm copies directly, not twelve
  yalms. Detection uses Flash's full practical range while FFXI still enforces
  the actual casting boundary.
  Leave EasyFarm's Battle, Job Ability, and Weaponskill lists disabled;
  PartyCombat handles shared engagement and AutoWS2 handles weaponskills.
- Force mode is deliberately capped at 30 yalms; it is not unlimited.
- Ordinary explicit force and `engageonceid` are sent once. Only the opt-in exact hidden-gauge
  route retransmits once after one second; it is not an ongoing command loop.
- PartyCombat does not automate weaponskills, rolls, ranged attacks, or
  defensive behavior.
